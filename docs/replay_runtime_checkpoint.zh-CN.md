# Replay 运行状态断点：实现状态

[English](replay_runtime_checkpoint.md)

Last materially modified: 2026-09-08
Last materially synchronized: 2026-09-08

Python tick 循环可以在一个事件执行之前暂停、保存运行对象图，再恰好恢复该事件一次。暂停不是维护停机：不撤单、不平仓、不重置 campaign，也不生成最终会计结果。

## F01 命令行

在原有、保持不变的单臂命令上使用 `--continuous --engine python --workers 1 --arms baseline`，再添加以下参数。时间戳仅为示例，实际截止时间必须位于输入区间内。

```bash
--checkpoint-at-ts-ms 1767229200000 \
--save-runtime-checkpoint /private/run/b0.runtime.pickle
```

成功落盘后输出 `status=checkpoint_saved`、`completed=false`，不会生成提前结算的 campaign、PnL 或资金费报告。使用相同日期、参数、数据和运行环境，移除上述两个参数并添加 `--resume-runtime-checkpoint /private/run/b0.runtime.pickle` 即可恢复；也可以同时指定下一个更晚的保存点。

自动分批执行使用 `--runtime-batch-seconds 21600 --runtime-batch-context-seconds 300 --save-runtime-checkpoint /private/run/b0.runtime.pickle`，不要同时传手动截断／输入范围参数。这些是资源配置示例，不是策略参数。每次持久保存后，进程替换自身，从同一断点加载下一批重叠输入；没有父进程保留旧数组，也不产生并行实验臂。每个断点路径只能有一个执行者，全程使用冻结的源码／运行环境目录。只有最后一批发布会计结果。某批失败时，最近一次成功保存的断点仍保留；用相同自动参数，再加指向该文件的 `--resume-runtime-checkpoint` 可恢复。不能把已完成结果再次恢复为新实验。调用方仍需选择批次大小和足以覆盖启用消费者的真实上下文；这不是自适应内存配置，也不能豁免缺失输入。真实十分钟冷启动窗口在第四、八分钟自动替换进程两次，决策、报价、成交、campaign 和资金费均与不中断执行完全一致；这不代表每个日期或供应商边界都已验证。

另一个真实原生盘口的一小时诊断跨越午夜，并在午夜自动保存：1,768 条决策、649 条报价、32 笔成交、12 个 campaign、资金费记录和汇总会计结果均与不中断执行一致。只有运行耗时和明确标注的本批输入元数据不同。诊断产物保存在私有证据库，不随公共仓库分发；这证明的是断点等价，不是历史 live 经济路径精确复现。

分批加载使用 `--runtime-input-bounds-ms START END`，两端均为包含在内的毫秒时间戳。完整会计日期仍由原来的 `--days` 定义；只加载与本批范围相交的日输入，每日输入先裁剪再拼接。第一批必须从原始会计起点开始。非最后一批必须在输入终点之前保存，保留真实的前视上下文；恢复批次必须保留截止事件、仍被引用的待处理游标和必要回看窗口。只有最终批次到达原始会计终点后才结算。

为验证跨午夜的短区间，F01 也支持 `--replay-start-ts-ms START --replay-end-ts-ms END --continuous`。包含式起点必须位于首个输入 UTC 日，包含式终点位于最后一日。实验账户从明确的起点初始化，不代表恢复历史 live 库存；完整来源和因果预热输入仍保留，区间外资金费被排除，局部窗口不会被计为完整 UTC 日。保存／恢复各批次时必须保持原始起止时间不变，`--runtime-input-bounds-ms` 只轮换其中加载的数据。省略起点时，仍使用既有的午夜起点。

执行成交行从明确起点裁剪，父消息的子成交索引按实际切片重新定位；来源与预热行不会变成起点之前的模拟成交。连续窗口内各日的质量资格可以不同：合并资格仅在每个组成日都明确通过时为真，`book_quality_by_day` 保留原始逐日结果。这不会取消来源／版本兼容性检查，也不会把不合格日升级。

每批输入来源记录随断点保存，并进入最终元数据。输入起点保持原始定时器网格；本批消息数和延迟摘要只描述加载输入，最终行明确标注此范围，不能当成全区间累计观察。即使裁剪执行行，也保留父消息完成所需的全部子成交时间。目前调用方仍需选择批次时长和上下文，尚未完成按内存自适应选择或整个 401 日多来源运行；每日准备过程在裁剪之前仍可能临时加载整日数据。不能把这些接口称为已经完成全区间 baseline，也不能用它们拼接独立的日度 fresh-start。

## Python 接口与状态边界

如果声明从空信号状态启动，而不是恢复历史 REST 预填，F01 支持在连续、fresh-start、Python 回放中使用 `--signal-cold-start`，并配合 `--runtime-compute-clock prediction_delivery`。初始已计算预测水位为空，等待与 live 共享的最少 300 根已完成一秒信号 Bar。完成进度按已到达的 aggregate-trade 回调推进，包括 live 生成的中间无成交 Bar；既不是第 300 行稀疏文件记录，也不是经过 300 秒墙钟。交易所／私有回调和既有安全时钟仍继续推进。这不会在行情缺口中伪造新鲜盘口。

首个来源 bucket、完成 Bar 数、正常报价时钟、预热状态和后续已计算 bucket 都随运行断点保存，包括预热尚未完成时的截断。恢复命令保持相同 cold-start 标志，已保存状态优先于空初始化。输出标明启动模式及主循环观察到预热完成的时间。在首个真实价格之前，空实验账户可以省略无价格、不能成交的定时器行；声明的进程／会计起点不变，不借用未来价格，也不能省略对账／系统事件。首个有价格事件单独报告。合成测试覆盖预热前后和移除尚未使用的预热期预测行；真实首个日历日的十分钟诊断，也通过了第四分钟截断并裁剪输入后的恢复对照。这不代表复原历史 live 启动或证明完整特征 DAG 等价；首次追赶计算仍使用声明的实测 catch-up 分层，不冒充单独实测的冷启动成本。完整 C++ tick 循环尚未实现此模式。

`simulate_tick(..., checkpoint_at_ts_ms=cut_ms)` 返回 `_replay_checkpoint`。使用 `models.replay.runtime_checkpoint_io` 中的 `save_runtime_checkpoint` 和 `load_trusted_runtime_checkpoint` 保存、读取，再通过 `resume_checkpoint=` 恢复。默认要求相同输入窗口；配合 `resume_input_batch=True` 可以换成具有不变重叠前缀的新窗口。

对象图保留订单共享引用、库存、会计、随机状态、未决 new/cancel、私有成交回调、HTTP/GLOBAL FIFO、计算阶段、策略状态、计数器和轨迹。原生订单簿迭代器从保存的文件内游标重新打开；已预取事件和已重建订单簿保留。运行进度回调由新进程提供。已排空订单状态的 `ContinuousReplayState` 是另一种局部会计快照，不能替代这个完整运行状态。

Python BUY/SELL 冷却适配器会保留 EMA、窗口、截止时间和计数器，仅重建进程锁。可选 native cooldown 热路径尚无状态导出，遇到它会拒绝，而不是静默换成新的 Python 状态；完整 C++ tick 循环和任意研究对象也不因此自动获得恢复能力。真实私有 B0 已通过代表性一小时的同一窗口恢复和实际输入裁剪对照，决策、报价、成交、campaign 及资金费与不中断运行一致。进程耗时和加载输入计数不要求相同；该测试不等于所有日期、跨供应商边界或可选策略均已验证。

丢弃旧输入前缀之前，适配器会把严格早于已保存下一事件的惰性 depth 回调按原始顺序补入既有 EMA，不额外评分、不生成成交。同时间或未来才到达的回调仍不能丢弃。真实跨午夜的有界输入对照也已通过，决策、报价、成交、campaign 和资金费表与不中断运行逐项一致；回归测试覆盖截断前长期没有新成交的情况。

### 保留来源差异的原始 L2 恢复

[现有盘口调度器](../models/exchange_book_replay.py)中的 `TardisExchangeBookTape` 读取明确指定的原始 Tardis L2 文件。它将跨 CSV 读取批次的一整条快照或增量原子分组，保留交易所时间和供应商接收时间，复用同一盘口重建实现。供应商时间不是部署主机延迟的实测值。组件遇到非法档位或来源时钟倒退会报错，不会重排记录或编造缺失事件。

这些记录不带 Binance 交易所序号，因此使用 `sequence_scope=provider_ordered`，不伪造 `U/u/pu`；严格交易所序号模式拒绝这种输入。模型诊断调度器可以应用并保存／恢复其盘口，但即使之后切回 native 来源，仍报告包含供应商顺序数据的证据范围。默认情况下，切换供应商需要真实快照，替换上一来源的盘口档位，不重置策略和账户状态。组件测试和短段真实重建对照不能证明全日历账户回测就绪。

F01 接受 `--exchange-book-source-plan`，读取包含 `symbol` 和 `days` 的 owner 本地 JSON。每天明确选择 `provider=tardis` 加 `raw_file`，或者 `provider=cryptohft` 加 `raw_root`，必须包含请求的输入日和预热日。这条路径要求 Python、diagnostic 盘口模式和 diagnostic 回测用途，不能与隐式 native 根目录同时使用，也不会自动更换供应商。两种来源复用同一调度器和运行断点；来源计划只读取一次，并记录摘要。处理后 BBO/L2 仍需单独选择，且必须与来源时钟匹配。

CryptoHFT 日期可明确选择 `recorder_snapshot_clock=preceding_update_id`。对于没有交易时间、记录时间恰为整点的快照，只有其末尾序号与紧邻的前一条真实增量一致时，才使用该增量时间作为快照状态时钟。原始事件／接收时间、盘口档位和所有增量均保留；无法匹配的时钟仍执行原有单调检查。首条快照可以读取前一原始小时的末条增量并记录其输入身份，使截断换批后的锚点保持一致。这是明确建模的快照状态时钟，不是实测交易所快照时间或 live 到达时间。默认仍为 `original`，原始小时缓存不变；组件测试覆盖断点和裁掉输入前缀后的行为。现有规范化命令支持 `--recorder-snapshot-clock preceding_update_id --timestamp-source transaction`，需使用独立产物目录、保留前序原始上下文并绑定生成的序号审计；分桶和序号时钟检查前使用同一个解析器。真实一小时对照覆盖 105,537 条来源消息，目标时钟倒退为零，终点前 20 档一致；这不是完整账户验证。完整日历 baseline 使用前仍需验证完整账户路径。

提供明确来源计划时，连续输入拼接允许逐日 `book_source_authority` 标签不同，汇总标为 `mixed_explicit_daily_sources`，并在 `book_quality_by_day` 保留各日原标签和资格。未提供计划仍拒绝来源标签不一致；成交来源、数据版本和 schema 兼容性检查不变，混合窗口不会继承其中某日的 native 资格。真实十分钟跨供应商诊断在午夜自动保存恢复后，203 条决策、67 条报价记录、资金费和汇总账目与不中断运行一致。此窗口没有成交，因此不能证明跨该边界的活跃 campaign 或已成交订单行为；其他路径由单独的 native 跨午夜和合成状态测试覆盖。该窗口刻意包含缺口，放宽的是历史覆盖率准入，不是 live 的 stale 盘口保护；它不是完整区间 baseline。

日文件的交易所时间可能重叠。如果下一文件以真实快照开头，显式来源计划在该快照的原始交易所时间交接，排除旧文件重叠的尾部；最多同时打开两个流式读取器，不改写原始时间戳。如果同供应商下一文件以增量开头，则保留这些更新，继续执行既有序号／时间检查；默认不允许无快照切换供应商。输入批次必须在处理交接之前包含下一文件，不能先消费重叠尾部并保存断点，再发现更早的快照。处理后 BBO/L2 也必须遵守相同来源选择；盘口组件相等不能单独证明跨供应商账户回放通过。

诊断计划可以在新接入的 CryptoHFT 日期明确设置 `handover: invalidate_then_delta_bootstrap`。在该日第一条真实事件时间，计划排除旧来源重叠尾部，先发出 `source_gap`，再应用新增量。这会清空旧盘口档位、使旧队列证据失效，但不编造快照、不假定没有证明的交易所序号连续性，也不重置账户。随后由既有非严格增量启动逻辑重建实际观察到的档位。该缺口保留在来源计数和断点游标中，即使下一输入批次从该日开始也一样。严格模式仍拒绝缺口。缺失档位、收敛和队列不确定性仍是限制，不能解释为真实零深度或精确 live。此路径只用于明确标注的模型化来源断点；完整区间 baseline 接纳前仍需比较其完整账户路径。

来源排除只应作用于它描述的输入。参考市场特征加载器不会再仅因该交易对／日期存在历史 CryptoHFT 盘口排除，就丢弃已经可用的官方成交 Bar；参考 BBO 加载器仍保留盘口检查。这不会编造缺失 Bar、接纳无效盘口或改写旧特征；改变来源选择环境时，应生成新特征产物。

现有 Tardis 规范化入口接受 `--timestamp-source exchange`，生成单独的 `normalized_tardis_l2_exchange_100ms_v1` 产物。每行只包含严格早于 100ms 右边界的交易所事件。时钟伴随文件保留原始供应商接收时间，但报告 `exchange_resample_age_us`，不再用供应商可见年龄；历史供应商传输耗时不会叠加到当前主机的模拟到达延迟。默认供应商时钟产物不变，即使 `--force` 也不能原位改变已有日期产物的时钟。原始时钟倒退不会被静默排序。这属于处理输入环境变化，旧冻结结果仍绑定原产物。

当前测试中的局部排名需要 120 秒历史成交，成交诊断可能读取未来 5 秒。其他启用的消费者可能需要更长上下文，未决订单或计算也可能引用更早的盘口。必须保留实际数据，不能用新造快照替代。每个来源的延迟抽样使用全局行号；`execution_message_delivery_params(..., prior_delivery=previous)` 保留已有消息到达时间和各连接的回调积压。每批覆盖统计不自动等于全区间覆盖报告，最终元数据必须保留各批来源记录。

自动分批还会保留报价、方差、预测及未决订单游标仍引用的真实输入。长期暂停可能需要超过配置的预留上下文：下一批只向前扩展读取范围，不改变保存事件或下一次截断时间。不为控制内存而清空游标、跳过延后的 EMA／BER 追赶计算。因此，分批时长不是硬内存上限；手工指定输入范围时仍需自行保留必要上下文。

## 持久化与验证

断点先写私有临时文件，flush/fsync 后原子替换，并同步目录；写入失败不覆盖前一个完整断点。文件使用 Python pickle，只允许读取自己可信进程生成的本地文件，禁止经 Studio 接收上传的 pickle。它不是跨平台交换格式，也不能替代既有配置和输入清单。

`tests/test_tick_runtime_checkpoint.py` 验证异步退出、在途成交、消息可见性、盘口前视及计算延迟下的重复保存／恢复。`tests/test_tick_runtime_input_window.py` 验证实际输入裁剪、数组游标、原生文件游标、策略和消息 FIFO 的连续性；F01 测试覆盖最终会计只运行一次。合成测试证明对应实现路径，不证明策略收益或所有私有配置都已通过。
