# F05 Offline Formal V22 Execution Design

Last materially modified: 2026-08-16

Status: `formal_v22_implemented_local_pre_admission`.

## Question

Formal-v22 asks whether the formal-v21 execution failure can be corrected without changing the admitted research question or reading an economic result: can every admitted opportunity first produce a C++-acceptable sparse target-support row, can the compiled owner predicates be derived inside the C++ runtime from the shared causal observation tape, and can every exception terminate with an atomic failure receipt?

## Scope

Formal-v22 is an execution-contract-only successor to formal-v21. It preserves exactly the same 30 family-specific historical Development days, 3,516 admitted mechanics opportunities, source and panel identities, opportunity identifiers, exact current-owner B0 control, eight legal side-specific duration arms, candidate ladder, four-by-three chronological folds, sequential repeated-policy estimand, `action_alpha_v1` statistics, and all evidence permissions.

The predecessor [formal-v21 execution contract](causal_multichannel_window_boolean_cooldown_full_multiscale_successor_offline_executor_cpp_one_shot_v1_contract_20260816.json) failed closed before a C++ lockstep arm was admitted because its real-day builder supplied one sparse target row with runtime-derived predicate values while the C++ startup contract required a contiguous full-width predicate tape. Formal-v22 corrects only that execution mismatch; it does not reinterpret or overwrite formal-v21.

Formal-v22 is not admitted merely because this design exists. Admission requires a clean public commit, a new annotated tag, a newly bound execution manifest, a formal-v21-to-v22 invariance receipt, the required tests, and the two pre-economic qualification receipts described below.

## Immutable Research Identity

The canonical source manifest, mechanics panel manifest, selected-day order, 3,516-opportunity identity set, fold manifests, exact B0 owner policy and predicate bundle, candidate ladder, duration vocabulary, estimand, score profile, statistical gates, and action/live permissions must compare equal to formal-v21 by content identity. Boolean declarations such as `data_changed=false` are insufficient without this field-by-field and hash-bound invariance receipt.

The only permitted differences from formal-v21 are the clean public commit, annotated tag, execution identity, qualification identity, versioned execution source files, rebuilt C++ extension bytes, execution manifest identity, and receipts produced by the corrected execution contract. Any other difference creates a new research identity and rejects formal-v22 admission.

## Engine Boundary

C++ authority remains limited to outer-train one-shot duration labels. Outer-test candidate evaluation and every sequential repeated-policy economic path remain Python-authoritative. One-shot effects may not be summed or substituted for the sequential estimand, and C++ may not be promoted to an outer-test or live engine under this identity.

The candidate-independent content-addressed day-input mmap and immutable observation-tape format may be reused only after their existing receipts and content hashes revalidate. No strategy-dependent staging, partial lockstep output, progress file, or qualification artifact from formal-v21 may be admitted into formal-v22.

## Zero-Economic Builder Walk

Before Python shared-prefix authority, any C++ arm, or any economic evaluator is invoked, formal-v22 must walk all 3,516 admitted mechanics opportunities in their frozen order. For every opportunity it must build the exact target-support row, validate the row against the admitted opportunity identity, compile the exact owner policy, and prove that the row is accepted by the same C++ startup contract used by formal execution.

This walk may read only outcome-blind mechanics, source receipts, policy identity, predicate-bundle identity, compiled predicate names, and execution metadata. It must not compute, load, expose, persist, hash for comparison, or use fills-after-treatment, terminal value, campaign PnL, scorecards, Validation, or sealed-holdout outcomes.

The walk passes only with exactly 3,516 unique accepted opportunity rows, unchanged opportunity ordering and identity, zero rejected rows, zero unknown predicate columns, zero economic evaluator calls, and an atomic immutable receipt whose status is `passed_all_3516_zero_economic_builder_walk`.

## Sparse Target-Support Row Contract

Each one-shot arm supplies only the row for its frozen target opportunity. A target row must carry a positive exposure-fill ordinal, fill-visible timestamp, side, campaign identity, snapshot or opportunity identity, support flags, channel-support flags, and fallback reason; these fields must exactly match the admitted mechanics opportunity.

Sparse target ordinals are legal and need only be strictly increasing within any multi-row input; they do not need to start at one or be contiguous. Duplicate, zero, negative, decreasing, mismatched, or unconsumed target rows fail closed.

An empty `predicate_values` vector has one meaning only: derive every policy predicate inside the C++ runtime from the shared causal observation tape and current campaign state. It is legal only when every policy predicate column belongs to the frozen compiled-owner set: `predicate::ema_pair_h4s_h16s:cross_age_le_slow`, `predicate::ema_pair_h16s_h256s:cross_age_le_fast`, and `predicate::m0::campaign_age_gt_control_duration`.

If any policy predicate is not in that compiled-owner set, the row must provide an exact-width tri-state vector in policy-column order. Empty vectors, width drift, invalid tri-state values, unknown predicate columns, or a runtime/compiler disagreement fail closed.

## Real-Day Lockstep

Only after the all-opportunity zero-economic builder receipt passes may the first admitted real UTC day run every admitted opportunity and all eight legal side-specific duration arms through Python and C++. The existing common full-path lockstep digest and zero-mismatch requirement remain unchanged.

The lockstep may compute path state solely to verify implementation parity, but it must persist no economic values and use no economic value for candidate selection. Its receipt must bind the clean commit, annotated tag, v22 execution manifest, v22 invariance receipt, source and panel manifests, exact B0 identities, C++ extension, observation tape, execution sources, digest implementation, opportunity count, arm count, and zero-mismatch count.

## Atomic Failure Receipt

Every exception after manifest binding, including source or hash drift, builder failure, predicate-contract rejection, policy compilation failure, observation-tape failure, C++ extension failure, worker submission or worker-result failure, Python authority failure, digest failure, receipt-write failure, and parity mismatch, must attempt one atomic fail-closed receipt before the process exits nonzero.

The failure receipt must record the execution and qualification identities, immutable input identities, failing phase, sanitized exception class and reason, completed and total opportunity/arm counts, whether any Python or C++ path began, whether economic values were computed, persisted, exposed, or used for selection, Validation and sealed-holdout read flags, and false action/live permissions. A receipt-write failure must leave an atomic quarantine marker and may never be interpreted as a passed or resumable qualification.

## Forbidden Operations

Formal-v22 must not modify or deploy EC2, create or enable a shadow, companion, observer, writer, or candidate telemetry path, modify the active owner policy, read Validation or sealed holdout, change the 30-day panel, replace B0, alter the candidate ladder, tune a duration or model, change the estimand or statistics, or grant candidate, action, or live authority.

## Admission

The minimum admission order is: close formal-v21 with an immutable failure receipt; land the execution-only correction and tests in a clean commit; create a new annotated v22 tag; bind a new v22 execution manifest without overwriting v21; validate the v21-to-v22 invariance receipt; pass the all-3,516 zero-economic builder walk; pass the first-day all-opportunity/all-arm lockstep; and then pass formal preflight. Any failure stops this identity without automatically creating formal-v23.

Formal-v22 remains offline Development infrastructure. Passing every execution gate authorizes only the unchanged frozen offline study; `action_authorized` and `live_authorized` remain false.
