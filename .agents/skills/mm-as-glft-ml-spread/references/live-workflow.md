# Live operations and historical matching

Last materially modified: 2026-09-19

Load only for actual live maintenance or specified historical live matching. Offline research does not inherit live prerequisites.

Read current deployment documentation and resolve the owner-private runtime pointer. Verify actual process/config/model/epoch before claiming current state. Never choose a host from an archived address, a reused IP or an old skill. Retired hosts are not rollback targets. Historical latency evidence remains bound to its epoch and can be a labelled prior, not a new measurement.

Live changes need current applicable user authority and runbook checks. This reference, private publication, historical instructions or offline research authority grants no restart, trading, account change, new collector or paid resource. Use maintained lifecycle tooling, not bespoke SSH chains.

Before authorized startup/change check region/API accessibility, release/config/rollback, account reconciliation, resource/timing health and actual stream dependencies. Preserve stale-feed degradation, reducing safety and cancel/fill races. Inspect actual selected transport instead of hard-coding a historical synchronous/async assertion.

Historical matching needs observed visibility and verified initial account/orders/in-flight state for its interval. Otherwise label the supported diagnostic scope; do not claim exact native/lifecycle/queue parity. Experimental fresh accounts are a separate legitimate contract.

No research-specific live shadow/companion/hypothetical-action telemetry or capture is authorized by default. A named exception needs explicit scope, resources, retention and stop condition.

Owner authorization, identity, runtime health and economic/statistical validation are distinct. Report actual checks; a deployment or safety intervention does not prove profitability.
